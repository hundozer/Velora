# Guest List pilot

A focused first implementation, separate from Take Us Out and Prague Scene listings. A community admin with MFA and `community:moderate` must confirm a real adult host and create a small gathering. No seeded nights or fake attendance; no host self-publication. The public Scene page links to the member Guest List; if none are confirmed, it offers existing published Scene listings.

An active adult member sends one private 20–500 character request per gathering. The host sees the requester and private pitch and can accept or decline. A database row lock serialises decisions so accepted places cannot exceed 2–12 configured capacity. Both directions of blocking, account status and age declarations are checked at decision time. Only an accepted active member with no block receives the address through a no-store server API; neither the public fields nor denied requests include it. The host/admin can cancel; a guest can withdraw, deleting the request and pitch. Cancellation hides the event and its address immediately on a fresh request, though already-read information cannot be recalled. An MFA admin can physically purge an ended night, address and all remaining requests. Host-profile erasure cascades to nights; applicant erasure cascades to their pitches.

Operational gate: find one real host and confirm the specific gathering, capacity, neighbourhood, time, address, accessibility and cancellation plan before publishing. Do not use sample profiles to imply an event exists. No payments, ticketing, precise public location or claim of attendance. No new scheduler or paid service. A real pilot also needs an operator to review requests/reports and purge ended gatherings; this version has manual admin tools and is not an automatic events marketplace.

Code scope: `guest_nights`, `guest_requests`, service-only `intimo_guest_request`/`intimo_guest_decide` RPCs, MFA admin API/workspace, adult-member API and Guest List page. Direct anon/authenticated table and function privileges revoked, RLS enabled. Server identity supplies applicant/host IDs. Exact address appears only on accepted, unblocked, active adult response. Tests cover API denials and disposable PostgreSQL role/capacity/block/state checks.

Staging verification (Supabase `fuczjjcwtxzzvoxilrme`, 2026-10-25): the exact SQL in `20261025115112_guest_list_pilot.sql` was applied with receipt `20261025115112 guest_list_pilot`. Inspection found both tables with RLS enabled and no policies, with table and RPC privileges for `service_role` only. `anon` and `authenticated` have neither direct table access nor RPC execute privileges. Two pre-existing legacy profiles and five `media_objects` remained; there were zero guest nights and zero requests after the migration. Hosted CI's disposable PostgreSQL job passed its role, block, capacity and state tests with rollback-only fixtures. The PR's verify and Preview smoke jobs passed on the preceding feature commit. These are schema and automated checks; no real host, member request, acceptance or address delivery has been exercised on staging. Production schema is unchanged by this work and must receive this migration before deploying the feature to members.
