## A. What exists today

**Works end-to-end in code, with Supabase and Auth0 configured:**
- Auth0 Universal Login, sign-up, logout, email verification gate and resend.
- Server-side actor resolution. Every member API derives identity from the
  encrypted Auth0 cookie, then looks up `profiles.auth_id`.
- 18+ declaration (`/api/access/age-declaration`) and onboarding wizard (nickname, DOB ≥18, single/couple, gender, orientation, country/city).
- Profile read/write via a single owner-only `/api/profile/me` with field allowlist.
- Member discovery (`/api/discovery/profiles`) and public anonymous directory (`/api/public/community`, `/people`).
- Profile pages, favourites/saved items, follow/"connections", mutual friendships.
- Direct messages (text only), conversation list, unread counts, read state, block checks, recipient message permissions.
- Dating ads ("Seznamka"-style, 28 categories, reply eligibility enforced server-side).
- Media: R2 presigned upload → complete → moderation status → authenticated delivery; albums with audience rules; participant/consent declaration step.
- Block, report (transactional), appeals, copyright notice, privacy export/deletion requests, consents, account deletion.
- Durable in-app notifications.
- Admin console (users, moderation, verification, privacy, audit, flags) with "God Mode" elevation and internal TOTP MFA.

**Partially works:**
- Discovery returns the newest 100 profiles. There is no server-side distance, online, age or gender filtering; filtering happens client-side over those 100. No Prague-first ordering exists.
- Messaging polls every 15 s. There is no realtime and no typing indicator. Images cannot be sent in DMs (`media_url` is always `null`).
- Notifications are in-app only. Nothing reaches a member who is not on the site, so no email for new messages: Resend is not configured in production and nothing triggers on messages.
- Online / last-active: `last_active_at` is read by discovery and admin views but **no route ever writes it**, so "recently active" filters always return nothing.
- Photo verification is admin-reviewed evidence. The flow exists, but the modal that described it is dead code.

**Mocked / dead (unreachable from any live route — 49 files, see `CLEANUP.md`):**
wallet, membership, checkout, tips, live streaming, creator studio, creators,
communities, events, referrals, `mockData.ts` (753 lines of fabricated
profiles/conversations), a complete second legacy auth layer (`apiMiddleware`,
`AuthorizationService`, `permissions`, `trustLevels`, `userModel`, `userSync`, the
in-memory `userStore` with localStorage persistence, `sessionStore`,
`destinationRouter`, `verificationEngine`), and fraud/ranking/payout/location-fuzzing
"engines". Middleware redirects the disabled routes to `/discovery`.

**Disconnected schemas:** `prisma/schema.prisma` (37 models: Wallet, LiveStream,
Subscription …, never imported), `db/schema.sql` (5 tables, unused),
`supabase/migration.sql` (legacy bootstrap with **"Allow all" RLS policies**).

**What a user can realistically do today:** open the landing page and confirm 18+,
then see empty content. Sign-in probably reaches Auth0, but provisioning fails
while the DB is hibernated. **Nothing in the core loop is usable in production
today.**

## B. Architecture assessment

```
Browser (Next 14 App Router, mostly "use client" pages)
  │  cookie: Auth0 encrypted session (appSession)
  │  localStorage: age-gate flag, language (display only)
  ▼
Next.js middleware ── Auth0 SDK middleware (/auth/*) + route redirects
  ▼
Next.js API routes (58) ── resolveServerActor(): Auth0 sub → profiles.auth_id
  │   in-memory rate limiter (per-lambda, ineffective on serverless)
  │   durable audit row on almost every write (incl. every message READ)
  ▼
Supabase Postgres via SERVICE-ROLE key (RLS bypassed; RLS = deny-by-default backstop)
  ▼
Cloudflare R2 (presigned PUT, authenticated GET proxy)   — prod env missing
Resend (email)                                           — prod env missing
Realtime: none (15 s polling)                            — Supabase Realtime unusable because auth.uid() is null under Auth0
```

**Duplication / confusion found:**
1. **Identity:** Auth0 (live) + a dormant second auth framework (in-memory store,
   JWT-ish `SessionManager`, `PasswordPolicy`) + `profiles.auth_id` text bridge +
   localStorage legacy keys (`velora_age_verified`). The live path is coherent
   (Auth0 → server actor), but the dormant code makes the system look like it has 3–4
   identity models.
2. **Schema:** four schema sources (Prisma, `db/schema.sql`, `supabase/migration.sql`,
   `supabase/migrations/*`). Only the last is canonical.
3. **Social graph:** `connections` (follow), `friendships` (mutual), `saved_items`
   (favourites) and the dead `connectionStore`/`visitorStore`. That is three persisted
   relationship tables for one MVP behaviour.
4. **Media:** legacy `photo_albums`/`videos` (JSON photo arrays, monetization
   columns) alongside canonical `media_objects`/`media_albums`/`media_album_items`.
5. **Chat:** `chat_messages` (rooms, unused) and `direct_messages`.
6. **Admin:** 8 admin roles, env-var role bootstrap, DB assignments, God Mode
   elevated sessions, internal TOTP with its own encryption key, and a separate
   `admin_action_events` + `audit_events` + `sensitive_access_events` trail. This is
   enterprise governance for a product with no members.
7. **Privacy engine:** retention rules/runs/holds/execution events and a cron
   worker. These are correct ideas, built 6 months early.
8. **Code form:** many files are minified one-line JSX/TS (e.g. `api/admin/albums`,
   `notifications/page.tsx`), which is effectively unreviewable.

**Score: 4 / 10.** The live request path (one session → server authorization →
Postgres) is sound, and the security instincts are good. It loses points for:
production not working; an identity provider that blocks the Supabase
platform features the product needs (RLS by `auth.uid()`, Realtime, Storage
policies); triple-duplicated domain models; four schema sources; ~25% dead code;
over-built governance; serverless-ineffective rate limiting; unreadable code
formatting; no realtime.

**Target architecture (simpler):**
```
Browser ──(Supabase Auth cookie via @supabase/ssr)──► Next.js (App Router)
   │                                                     │ server components / route handlers
   │                                                     │ createServerClient(cookies) → user-scoped queries (RLS)
   │                                                     │ service-role only in admin + cron code
   ▼                                                     ▼
Supabase Realtime (DM inserts, presence) ◄──── Supabase Postgres (RLS by auth.uid())
                                                         │
                                  Cloudflare R2 (media, presigned)  +  Resend via Supabase Auth SMTP and app email
```
One identity (`auth.users.id`) = `profiles.id`. One session (Supabase cookie). One
authorization model (RLS + thin server checks). One schema source
(`supabase/migrations`). Details: `ARCHITECTURE.md`.

## C. Product assessment

- **Direction:** half right. The free, adults-only, safety-first, server-authoritative
  posture is right. The *shape* is wrong: effort went into compliance
  machinery, admin governance and future monetization, while the
  return-visit loop received almost none.
- **Misunderstood:** Amateri is not sticky because of profiles. It is sticky because of
  (a) a constant flow of new amateur photos with comments and ratings, (b)
  regional dating ads with explicit intent ("tonight in Prague"), and (c) "who
  viewed me" and other social feedback that pulls people back. Intimo built a
  directory plus inbox.
- **Overbuilt:** God Mode, 8 admin roles, internal MFA, retention engine, triple
  audit trails (including an audit row per message *read*), 28 dating-ad categories,
  6 UI languages, explicit-media participant declarations before any users exist.
- **Underbuilt:** working production, realtime messaging, email notifications,
  "visitors / interest" feedback, Prague-first discovery with distance and online-now,
  private-photo access requests, image messages, empty-state strategy, and a real
  landing page that explains the product.
- **Missing from the loop:** every *return trigger*. Nothing brings a member back:
  no email on message, no "someone viewed / liked you", no new-in-Prague digest.
- **Delete:** everything listed under DELETE NOW in `CLEANUP.md`.

## E. Answers to the 12 questions

1. **MVP completion:** ~50% of the MVP exists as code that would work if
   deployed correctly. **~0% is usable in production today** (DB hibernated; R2 and
   Resend missing in production; schema parity unknown). The weakest part is the
   return loop (notifications, realtime, visitors), at ~10%.
2. **Looks complete but isn't:** the home page and `/people` (no data), media
   upload (no R2 env in prod), email verification resend and notifications
   (no Resend in prod), messaging "real-time" (15 s polling, text only), discovery
   filters (client-side over newest 100), the admin console (depends on unapplied
   migrations), and online status (never updated).
3. **Product direction:** partially. Keep free / adults / safety. Shift effort to
   intent (ads/plans), feedback (visitors, interest, likes on photos) and return
   triggers (email, realtime).
4. **Architecture direction:** the server-authoritative instinct is right; the
   Auth0 + service-role design is a dead end for realtime, RLS and storage. Converge
   on Supabase.
5. **Delete immediately:** the 49 unreachable files, Prisma, `db/schema.sql`,
   `supabase/migration.sql`, legacy auth tests, the empty Vercel `intimo` project,
   and the hardcoded Supabase URL/key in `src/lib/supabase/client.ts` (see
   `CLEANUP.md`).
6. **Replace Auth0 with:** **Supabase Auth** (email + password, magic link,
   confirmation and reset emails through Resend SMTP, built-in TOTP MFA for admins).
   See `ARCHITECTURE.md` §ADR-002.
7. **Next 5 things to build:** (1) restore production (wake/upgrade DB, apply and
   verify migrations, set R2 and Resend in production); (2) Supabase Auth migration
   plus RLS; (3) Realtime DMs with image messages and email notification on new message;
   (4) Prague-first discovery (distance, online-now, recently active, server-side
   filters) plus "visitors" and "interest"; (5) "Plans" (simplified dating ads, ≤6
   categories, 24–72 h expiry) wired into home and notifications.
8. **Amateri features Intimo needs:** couple profiles, rich "looking for", photo
   albums with private access, regional dating ads, profile visitors,
   comments/likes on photos, verification badge, block/report, regional discovery.
9. **Amateri features not to build yet:** chat rooms, webcams/video chat,
   videos, blogs/stories/magazine, forums, contests/top lists, VIP/credits,
   groups and events.
10. **Biggest technical risk:** possibly-unapplied RLS lockdown. Production
    historically had `Allow all select/insert/update` policies on `profiles`, and
    the publishable key is committed in git. If the lockdown migration was never
    applied, member emails, DOBs and profile writes are exposed to anyone. **Verify
    the moment the DB is awake.** The second risk is that the DB hibernation and schema
    drift mean nobody can currently state what production's schema is.
11. **Biggest product risk:** cold start in Prague. A profile grid with 30 people
    reads as dead. Without intent posts, visitor and interest feedback, and email
    return triggers, early members will not come back.
12. **Shortest credible path to repeat Prague users:** Phase 0 (≈1–2 weeks):
    restore prod, Supabase Auth, delete dead code. Phase 1 (≈3–4 weeks): realtime
    DMs with email, Prague discovery, visitors and interest, Plans, private albums, PWA.
    Then a seeded, invite-only launch of 100–200 hand-recruited Prague members
    (couples and women first), with weekly "new in Prague" emails, measured by
    D7 return and messages per active member.
